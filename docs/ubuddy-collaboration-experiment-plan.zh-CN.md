# uBuddy 跨人协作原型与完整实验方案

## 1. 当前方法生命周期

本原型按以下顺序运行：

1. 每个用户的 uBuddy 在协作发生前独立建立、维护并发布能力画像。
2. 委派者根据可见范围查询候选 uBuddy，而不是先建群再要求成员发布画像。
3. 系统根据任务要求计算基础匹配分，并在存在已验证历史协作证据时给出进化后的排序分。
4. 委派者选择接收者时，系统验证画像仍然有效，并固化不可变的能力选择快照。
5. 选择完成后才创建直接委派或协作任务实例；任务实例引用选择快照。
6. 执行期间聚合依赖、进度、私有工作区活动摘要、需求修订和结果版本。
7. 任务结束后生成组织层与个体层信号，经证据门控后进入下一轮候选排序或能力更新。

能力画像是长期资源，任务实例是一次协作样本，选择快照是二者之间不可变的历史连接。

## 2. 当前代码获得的数据

### 2.1 委派前候选查询

接口：`POST /api/collaboration/candidates/query`

输入：

- 候选用户 ID；
- 任务描述；
- 所需能力标签；
- 任务类型；
- 交付物类型；
- 偏好任务类型。

输出：

- `queryId`：本次候选查询的稳定标识；
- 可见候选与不可见候选；
- 画像版本、内容哈希、发布时间和访问范围；
- 基础能力匹配分；
- 已验证历史证据数量、正负证据数量；
- 进化调整量和进化后排序分；
- 匹配字段、缺失字段和冲突字段。

接口：`POST /api/collaboration/selections/confirm`

该接口在建群前确认一次选择，返回 `selectionId`、签名选择凭据和可直接传给建群/委派接口的 `delegationInput`。当前选择确认采用无新增表的签名快照；真正创建委派时仍会重新检查画像是否 active、revision 和 contentHash 是否一致。

### 2.2 委派时能力选择快照

存放在 `agent_delegations.metadata_json.capabilitySelectionSnapshot`，包括：

- 选择者和接收者；
- 查询 ID；
- 选择时间和选择理由；
- 当时的任务需求；
- 被考虑的候选集合；
- 接收者画像版本、内容哈希、可见范围和公开能力摘要；
- 委派者自己的画像摘要（存在时）。

快照不会跟随画像后续更新而变化。若候选查询后画像被撤回或替换，显式携带旧版本创建委派会返回冲突，要求重新查询。

### 2.3 协作状态投影

接口：`GET /api/collaboration/state-graph`

输出：

- uBuddy 节点和委派边；
- 当前可见画像；
- 委派时的历史选择快照；
- 委派状态；
- 私有工作区活动数量摘要；
- 依赖关系；
- 结果版本及 `superseded`、`pending`、`adopted` 等决策。

私有会话正文、Memory、本地路径和未确认草稿不进入共享投影。

### 2.4 过程归因与进化路由

接口：`GET /api/collaboration/attribution`

输出：

- 从画像选择、任务创建、执行失败、重试、修订、提交到验收的事件链；
- 组织层信号，如委派路径有效、画像选择有效、需求修订模式；
- 个体层信号，如交付能力得到支持或出现能力缺口；
- 进化证据引用；
- 个人候选、集群候选和阻断原因。

缺少选择快照、画像证据或进化证据时，系统返回阻断原因，不生成伪高置信度结论。

接口：`POST /api/collaboration/attribution/:delegationId/evolution-route`

该接口把达到置信度阈值的归因信号路由到现有 Evolution 证据体系。个人进化只能由对应 Agent 所有者本人触发；组织层信号只记录为集群/组织候选证据，由现有云端调度器负责后续运行。返回 `routedEvidence`、`personalRuns`、`organizationRoute` 和 `blockedReasons`。

证据路由、状态投影和规则归因本身不需要大模型。真正生成 Skill/Memory 进化候选时需要 Responses API 兼容的模型 Provider；未配置时接口保留证据并明确返回 `evolution_model_unavailable`，不会假装完成了模型进化。

本地开发支持直接复用 `OPENAI_BASE_URL` 和 `CRS_OAI_KEY`。如果没有显式设置 `JANUS_EVOLUTION_MODEL` 或 `OPENAI_MODEL`，本原型默认使用已验证可用的 `gpt-5.4-mini`；生产环境仍建议显式指定模型和通过 Secret 文件注入密钥。

接口：`GET /api/collaboration/evolution-impact?delegationId=...`

该接口把某次协作的归因、证据、Evidence usage 和 Evolution run 汇总到同一个实验视图，便于测量“协作结果是否真正进入下一轮进化”。

## 3. 当前本地验证结果

运行：

```powershell
cd D:\Cli-anything\Janus
npm run cloud:test:collaboration-research
```

2026-08-20 的原型测试获得：

| 数据项 | 实际结果 |
|---|---|
| 可见候选 | Bob、Carol |
| 不可见候选 | Dave |
| 选择时画像版本 | Bob revision 1 |
| 当前画像版本 | Bob revision 2 |
| 历史快照是否保持 | 是，仍为 revision 1 |
| 状态图节点/边 | 4 / 3 |

这项测试证明了数据链路、版本不变性、可见性过滤、结果版本处理、归因输出和最小进化反馈可以运行。它不等于论文方法有效性结论。

## 4. 完整实验总览

实验分为四层，必须按顺序完成。

| 层级 | 要回答的问题 | 结论边界 |
|---|---|---|
| A 架构通路 | 是否能正确获得、保存和返回数据 | 工程可行性 |
| B 协作决策 | 状态投影是否改善选人、分工和依赖协调 | 创新点一有效性 |
| C 归因准确性 | 是否正确区分组织、匹配和个体原因 | 创新点二机制有效性 |
| D 下一轮进化 | 归因经验是否改善新任务 | 联合进化效果 |

## 5. 实验 A：架构与数据通路验证

### 5.1 假设

- A1：建群前可按权限查询预先存在的 uBuddy 画像。
- A2：委派创建时能固化正确的画像版本。
- A3：画像后续更新不改变历史快照。
- A4：状态投影完整返回公共状态且不暴露私有内容。
- A5：完整轨迹能进入组织/个体归因和进化路由。

### 5.2 测试样本

至少准备：

- 4 个用户；
- 3 个已发布画像，其中包含 friends、organization 和不可见关系；
- 1 个多依赖任务；
- 1 次画像升级；
- 1 次失败后重试成功；
- 1 次需求修订；
- 1 个 superseded 结果和 1 个 adopted 结果；
- 组织层和个人层各至少 1 条已验证进化证据。

### 5.3 通过条件

- 候选可见性准确率 100%；
- 历史快照版本保持率 100%；
- 状态字段完整率 100%；
- 私有正文和本地路径泄露率 0%；
- 旧结果误发布率 0%；
- 缺证据样本的高置信度进化路由率 0%。

## 6. 实验 B：共享状态对协作决策的影响

### 6.1 自变量

| 组别 | 委派前信息 | 执行中信息 |
|---|---|---|
| B0 Local-only | 仅自身记录 | 仅收到的消息 |
| B1 Static-profile | 静态能力画像 | 普通消息 |
| B2 Shared-message | 静态画像与群消息 | 共享消息，无统一版本/依赖状态 |
| B3 Ours | 带版本、可见性和历史证据的候选投影 | 统一状态、依赖和结果版本投影 |

底层模型、提示词、候选集合、任务输入和运行预算保持一致。

### 6.2 任务集

建议建立 120 个协作任务实例，分为四类，每类 30 个：

- 数据分析与报告；
- 资料调研与写作；
- 代码修改与测试；
- 汇报材料生成与审核。

每个任务含 3—5 个子任务、2—4 名候选者、至少一条依赖，并随机注入一种扰动：画像过期、候选不可见、能力错配、需求修订、失败重试或旧结果残留。

每个组至少运行 5 个随机种子。若使用真实参与者，应对任务顺序做拉丁方平衡，避免学习效应。

### 6.3 指标

- Top-1 协作者选择准确率；
- 能力错配率；
- 过期画像使用率；
- 依赖违规率；
- 重复劳动次数；
- 读取 superseded 结果次数；
- 返工次数；
- 任务完成率；
- 完成时间、token 和调用成本；
- 私有信息泄露率。

### 6.4 主要判据

B3 相比 B1 和 B2，在不增加隐私泄露的条件下显著降低能力错配、依赖违规和过期结果使用。使用 bootstrap 95% 置信区间；二元指标采用混合效应 logistic 回归，任务 ID 和随机种子作为随机效应。

### 6.5 消融

- 去掉画像版本；
- 去掉能力选择快照；
- 去掉依赖状态；
- 去掉结果版本；
- 去掉可见性过滤；
- 去掉历史进化证据排序。

## 7. 实验 C：过程归因准确性

### 7.1 金标准故障类型

构造可控轨迹，并在生成轨迹时记录真实原因：

- 任务拆分错误；
- 协作者选择错误；
- 能力画像过期或虚假；
- 依赖顺序错误；
- 个体 Agent 能力不足；
- 外部工具或上游输入故障；
- 需求变更导致旧结果失效；
- 证据不足，不能归因。

建议每类至少 25 个，共 200 个样本；其中至少 20% 包含两个共同原因。

### 7.2 对照组

- C0：只看最终结果；
- C1：查看完整自然语言轨迹；
- C2：普通单层信用分配；
- C3：本文的组织—个体双层过程归因。

### 7.3 指标

- 原因分类 macro-F1；
- 组织/个体归因混淆率；
- 证据引用 precision、recall；
- 多原因轨迹的 attribution IoU；
- 置信度校准误差 ECE；
- 应阻断样本的阻断准确率；
- 错误经验进入进化候选的比例。

至少由两名标注者独立检查 20% 样本，报告 Cohen's kappa。

## 8. 实验 D：联合自进化效果

### 8.1 两轮设计

第一轮执行训练任务，收集协作轨迹和结果；第二轮执行任务类型相同但输入不同的测试任务。第二轮禁止直接复用第一轮答案，只能使用结构化经验。

| 组别 | 组织策略更新 | 个体画像/能力更新 |
|---|---:|---:|
| D0 Static | 否 | 否 |
| D1 Organization-only | 是 | 否 |
| D2 Individual-only | 否 | 是 |
| D3 Joint | 是 | 是 |
| D4 Joint-no-gate | 是 | 是，但不做证据门控 |

### 8.2 当前原型已经能验证的最小闭环

当前实现将已验证历史协作证据汇总为 `experienceSupport`，对下一次候选排序进行有限调整：

```text
基础画像匹配分
  + 已验证成功证据加权
  - 已验证失败证据加权
= 下一轮 evolvedScore
```

本地样本中 Bob 的基础分为 0.7778，两条已验证成功证据使下一轮分数变为 0.8578。这证明反馈通路实际影响了下一轮决策变量，但尚不能证明真实任务成功率提高。

### 8.3 论文级完整闭环

- 组织更新：更新任务分解模板、委派路径和依赖模板；
- 个体更新：更新能力画像置信度、Skill 候选或 Memory 候选；
- 门控：只使用通过验证且置信度超过阈值的证据；
- 回滚：第二轮表现下降时撤销该经验；
- 冷启动：没有证据时退回基础画像匹配分。

### 8.4 指标

- 第二轮任务成功率提升；
- 相对 B3/D0 的错误委派减少率；
- 返工和依赖等待时间下降；
- 经验迁移收益；
- 负迁移率；
- 错误画像更新率；
- 错误组织策略采用率；
- 门控后的净收益；
- 回滚恢复率。

### 8.5 有效性判据

- D3 显著优于 D0；
- D3 同时优于或不劣于 D1、D2，证明联合更新不是单侧更新即可解释；
- D3 优于 D4 的安全指标，证明证据门控有价值；
- 在未见过但同类型的任务上仍有收益，排除只记住具体答案。

## 9. 运行与产物规范

每次实验保存：

- `config.json`：组别、模型、种子、阈值和数据版本；
- `tasks.jsonl`：任务、候选和注入故障真值；
- `candidate_queries.jsonl`：查询、可见性、基础分和进化分；
- `selection_snapshots.jsonl`：画像选择快照；
- `traces.jsonl`：协作事件链；
- `attributions.jsonl`：组织/个体信号及证据引用；
- `evolution_updates.jsonl`：采用、阻断和回滚记录；
- `metrics.json`：聚合指标；
- `errors.jsonl`：失败样本和人工分类。

所有样本使用匿名用户 ID，不保存私有聊天正文、本地路径或未公开 Memory。

## 10. 结论边界

当前代码已经证明：正确生命周期可以落地，所需数据能够获得，状态和归因接口可以运行，已验证证据可以改变下一轮候选排序。

尚未证明：真实跨人任务中任务成功率、效率或能力演化质量显著提升。该结论必须通过实验 B、C、D 的多任务、多随机种子和统计检验获得，不能由单元测试替代。
