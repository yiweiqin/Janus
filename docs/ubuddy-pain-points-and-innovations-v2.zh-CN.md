# uBuddy 跨人 Agent 协作：痛点与新创新点（研究版）

## 摘要

跨用户、多组织、多 uBuddy 协作与普通的多 Agent 协作不同：参与者不属于同一个完全信任域。协作需要共享任务目标、约束、结果状态和证据，但参与者又不能直接看到彼此的私有 Prompt、Memory、文件、身份信息和内部推理过程。

本文将问题概括为两个痛点，并提出两个相互连接的创新点：

1. **隐私约束下的自适应最小充分披露**：系统不预先写死“所有任务都共享哪些字段”，而是根据当前下游决策、上游可披露内容和隐私风险，逐步寻找足以支持正确决策的最小信息集合。
2. **基于渐进式双树、逆向谱系因果干预与最小差异修复的组织—个体联合进化**：系统保存逐步形成的规划 DAG 和真实执行 DAG，用谱系连接输入、输出和结果版本；失败后先定位多个根因候选，再通过局部反事实干预验证原因，并搜索成本最小、可复用的规划/契约/Agent 修改，最后同时更新组织策略和个体 Agent 能力。

这里的目标不是让系统把所有信息都公开，也不是让规划图机械地复制成功执行图，而是在不同信任边界下，用尽可能少的信息完成可靠协作，并从多任务证据中逐步得到更好的协作策略。

---

## 一、痛点

### 痛点一：跨人协作同时受到“信息不足”和“信息过多”的双重约束

现有很多多 Agent 框架默认参与者处于同一信任域：Agent 可以共享完整任务描述、对话上下文、Memory、文件和中间结果。跨用户 uBuddy 协作则不满足这一假设。

例如，Alice 的 uBuddy 将市场分析任务交给 Bob 的 uBuddy，Bob 又把数据任务交给自己的 Agent。Carol 的图表 Agent 可能需要知道“数据是否覆盖 2025 年、是否经过来源验证、当前使用哪个版本”，但不应该因此看到：

- Bob 与用户的完整私聊；
- Bob 的私有 Prompt 和长期 Memory；
- 原始文件中的无关个人信息；
- 真实文件路径、凭据和内部系统地址；
- 尚未获得授权的原始数据。

于是出现两种相反的失败。

#### 1. 披露不足

下游只收到一句“数据已完成”，却不知道：

- 结果覆盖的时间范围；
- 来源是否经过验证；
- 哪个结果版本是最新版本；
- 哪些字段仍然缺失；
- 结果能否用于正式交付，还是只能用于草稿。

后果包括版本错配、重复劳动、错误等待、错误复用和约束丢失。

#### 2. 披露过度

为了避免信息不足，系统把完整上下文、原始文件或私有 Memory 直接发送给下游。这样虽然可能提高短期任务成功率，却增加隐私泄露、越权访问、无关信息传播和通信成本。

#### 3. 现有机制的不足

blackboard、消息总线、任务 DAG、共享 Memory 和 provenance 系统分别能够解决部分问题，但通常没有同时解决以下问题：

1. 不同用户属于不同信任域；
2. 每个下游 Agent 的信息需求随任务和当前决策变化；
3. 共享内容需要带版本、证据、不确定性和适用范围；
4. 系统需要证明某一信息是否真的被下游决策所需要；
5. 共享状态既要支持协作，又要限制私有信息的推断和泄露。

因此，问题不是简单的“有没有共享状态”，而是：

> 在跨用户信任边界下，如何选择对当前决策足够、对隐私暴露尽可能少的协作信息？

这个问题可以通过以下指标进行测量：

- **任务效用**：任务成功率、质量、完成时间和成本；
- **披露量**：共享 token 数、字段数、文件字节数或查询次数；
- **隐私风险**：从公共状态推断私有字段的攻击成功率、敏感字段暴露率；
- **协作错误**：版本错配、约束丢失、重复劳动和不必要等待的比例。

---

### 痛点二：只看最终成功/失败，无法判断组织、个体还是基础设施出了问题

多 Agent 任务的最终结果通常由一条长链路共同产生：

```text
需求理解 → 任务拆解 → 协作者选择 → Agent 分配
→ 信息交接 → 依赖满足 → 执行与重试
→ 结果版本管理 → 下游消费 → 最终验收
```

如果只保存最终答案和最后一个失败节点，系统很容易产生“末端责任偏差”：把错误归给最后执行的 Agent，而忽略更早发生的影响因素，例如：

- 用户需求中的时间范围没有被传递；
- 组织拆解时漏掉了来源验证；
- 选择了不匹配或高负载的协作者；
- 交接时只传了摘要，没有传输出约束；
- 下游使用了旧结果版本；
- 验收器漏检了内容错误；
- 网络、工具、存储或模型服务发生故障。

同时，一个失败任务也可能包含局部正确行为和有效补救行为。例如上游数据 Agent 输出质量不足，但验证 Agent 正确发现问题，另一个 Agent 又通过补充数据修复了部分错误。若系统只给最后结果贴“失败”标签，这些可复用经验都会丢失。

因此，第二个痛点是：

> 如何从规划、执行、输入输出谱系和验收结果中区分多个原因，判断哪些偏差真正传播到了最终结果，并把修改交给正确的组织层或个体 Agent？

这个问题需要测量：根因定位准确率、错误传播路径识别率、误惩罚率、修复后的跨任务收益和修复成本。

## 二、创新点一：面向决策的反事实自适应最小充分披露

### 2.1 核心思想

系统不采用固定规则，例如“所有任务一律共享 quality、freshness、risk 三个字段”。因为不同任务、不同 Agent、不同阶段真正需要的信息不同。

系统采用“先抽象声明、再按需补充、达到决策稳定即停止”的方式：

```text
下游提出当前决策问题
  ↓
上游生成可披露的声明、证据和不确定性
  ↓
系统先披露低敏感度摘要
  ↓
下游判断信息是否足以做出当前决策
  ↓ 不足
请求最小的下一项信息或受控查询
  ↓ 足够
停止披露并记录本次披露理由
```

系统传递的不是“完整内部状态”，而是与当前决策相关的**声明（claim）**。例如：

```text
声明：数据覆盖 2025 年全年
声明：数据来自三个公开来源
声明：来源一致性检查已通过
声明：当前版本为 result_v2
声明：结论置信度为 0.82，异常项有两个
```

原始文件、私有 Memory 和身份信息可以继续隐藏。必要时只允许下游在受控环境中执行批准的查询，而不是直接读取完整数据。

### 2.2 方法：反事实驱动的自适应披露算法

可将该方法称为 **CAD（Counterfactual Adaptive Disclosure，反事实自适应披露）**。它不把字段列表写死，而是针对每一次具体决策动态选择披露内容。CAD 的输出也不是唯一固定字段集合，而是一个带适用范围的披露策略：在什么任务、什么决策、什么权限和什么风险预算下，公开哪些声明以及采用何种访问方式。

#### 输入

- 下游 Agent 当前要做的决策 (q)，例如“能否开始制作正式图表”；
- 下游的任务契约和验收条件；
- 上游可公开的声明、证据引用、版本信息和不确定性；
- 上游私有字段及其敏感度；
- 用户和组织的披露策略；
- 当前任务允许的通信成本和隐私预算。

#### 核心步骤

1. **决策需求解析**：把“我能不能使用这个结果”转换成所需的判断条件，例如版本是否最新、时间范围是否满足、质量是否经过审核。
2. **候选信息生成**：上游为每个判断条件生成多种披露单元：低精度声明、统计摘要、哈希/承诺、验证证明、受控查询接口或原始字段。
3. **低敏感度优先**：先尝试披露风险较低的声明和证据引用。
4. **反事实测试**：模拟“不披露候选信息 (x)”时，下游是否仍能稳定作出正确决策。如果不披露也能正确决策，则不披露 (x)。
5. **增量披露**：如果不能稳定决策，则选择预期收益最高、隐私风险最低的下一项信息，继续披露或开放一次受控查询。
6. **停止条件**：当下游决策在多次模拟、不同合理解释和不确定性扰动下保持一致，或者达到隐私预算/权限上限时停止。
7. **记录证据**：保存本次披露的字段、理由、决策需求、隐私风险、下游是否消费、结果版本和证据引用。

#### 可执行伪代码

```text
输入：
  q       当前下游决策
  C       候选披露单元集合
  policy  用户权限与隐私策略
  budget  隐私、通信和计算预算

S = 最低风险的公共声明集合

while 未达到预算上限：
    stability = EvaluateDecision(q, S)

    if stability >= 决策稳定阈值：
        S_min = RemoveRedundantClaims(q, S)
        返回 S_min、决策置信度和披露理由

    对每个仍可披露的候选 x：
        gain[x] = EvaluateDecision(q, S ∪ {x}) - stability
        risk[x] = EstimatePrivacyRisk(S ∪ {x})
        cost[x] = EstimateDisclosureCost(x)
        score[x] = gain[x] - λ·risk[x] - μ·cost[x]

    x* = 满足权限约束且 score 最高的候选

    if 不存在合法的 x*：
        返回 information_insufficient，
             并请求用户授权、降低任务要求或改用受控查询

    S = S ∪ {x*}

返回 privacy_budget_exhausted，不允许 Agent 猜测隐藏内容
```

其中 `EvaluateDecision` 不应只询问同一个 Agent 一次。它可以通过多次采样、不同提示表述、规则验收器、辅助评估模型或历史相似任务估计：只看到当前信息集合时，下游决策是否稳定且正确。`RemoveRedundantClaims` 再逐项删除已经选择的信息，检查决策是否仍然稳定，以避免贪心搜索留下不必要字段。

#### 为什么不是写死规则

不同任务的候选集合和判断条件来自当前任务契约、验收条件、依赖状态与下游的具体决策。例如：

```text
市场报告任务可能需要：时间范围、来源验证和结果版本；
代码修复任务可能需要：复现步骤、错误栈、测试结果和代码版本；
医疗预约任务可能需要：可用时间段和授权状态，但不需要完整病历；
财务审核任务可能需要：合规证明和金额区间，但不需要交易方真实身份。
```

系统可以从历史任务学习某类决策经常需要哪些声明，以缩小候选搜索空间；但历史策略只能提供先验排序，不能直接绕过本次任务的权限检查和反事实测试。

可以用一个简单目标表示信息选择：

\[
\max_{S \subseteq C} U(q,S)-\lambda R(S)-\mu Cost(S)
\]

其中：

- (C) 是候选披露单元集合；
- (S) 是本次实际披露的集合；
- (U(q,S)) 是信息对当前决策正确性的帮助；
- (R(S)) 是隐私泄露风险；
- (Cost(S)) 是通信、计算或查询成本；
- (lambda)、(mu) 由任务的隐私和成本要求决定。

这个公式不是要求系统永远使用固定权重，而是明确“任务效用、隐私风险和成本”三者之间的优化目标。

其中隐私风险不能只靠人工填写。可以组合使用：敏感字段规则、用户自定义等级、从公开摘要反推私有属性的攻击模型、成员推断/属性推断成功率，以及声明之间组合后产生的额外泄露风险。这样可以识别“单个字段看似安全，但多个字段组合后能够推断身份”的情况。

### 2.3 传递格式

每一次披露可使用以下统一结构，而不是只传一段自然语言：

```json
{
  "claim": "数据覆盖 2025 年全年",
  "claimType": "time_coverage",
  "scope": "result_v2",
  "uncertainty": 0.03,
  "evidenceRefs": ["validation_4"],
  "privacyLevel": "low",
  "disclosureReason": "下游需要判断能否制作正式图表",
  "counterfactual": {
    "withoutThisClaimDecisionAccuracy": 0.61,
    "withThisClaimDecisionAccuracy": 0.94
  },
  "accessMode": "summary"
}
```

可选的访问模式包括：

- **分层摘要**：普通参与者看到完成状态，直接下游看到版本和适用约束，审核者看到证据摘要，所有者才能看到原始内容；
- **可验证声明**：只公开结论和哈希、审计记录或验证证明，不公开原始数据；
- **受控查询**：下游提交“需要什么信息以及为什么需要”，系统返回允许的统计量或布尔判断；
- **承诺后披露**：先提交结果哈希或承诺，必要时再披露原文，防止结果事后被修改；
- **不确定性携带**：声明同时携带置信度、未知项、适用范围和过期时间。

### 2.4 该创新与已有共享机制的区别

已有共享 Memory 或 blackboard 主要回答“把什么内容放到公共区域”。CAD 进一步回答：

1. 当前这个下游决策具体需要什么信息；
2. 不公开某个字段时，决策是否仍然可靠；
3. 应先公开声明、证明、统计量还是原始字段；
4. 本次披露是否真的被下游使用；
5. 如何在不同任务中自动得到不同的最小披露集合。

因此，创新点不在于“文本、图或文本+图”哪一种媒介，而在于**面向决策的、可验证的、反事实驱动的信息披露策略**。

### 2.5 需要验证的研究假设

- 在相同隐私风险下，CAD 比完全共享和固定字段共享取得更高任务成功率；
- 在相同任务成功率下，CAD 减少 token、文件传输量和敏感字段暴露；
- CAD 能降低结果版本错配、约束丢失和重复劳动；
- 不同任务会得到不同的最小披露集合，证明该方法不是写死规则。

## 三、创新点二：基于渐进式双树、谱系因果干预与迭代最小差异修复的联合进化

### 3.1 三类证据结构

#### 1. 渐进式规划 DAG (P)：原本准备怎样完成

发起方 uBuddy 通常只知道最终目标和主要约束，并不知道接收方组织内部有哪些 Agent。因此规划不是一次性生成，而是逐步展开：

```text
P0：完成市场分析报告
P1：数据收集 + 竞争分析 + 图表 + 汇总
P2：数据收集 = 获取数据 + 清洗数据 + 验证来源
P3：因需求或新证据产生重新规划
```

每个版本保存需求版本、规划者、规划器版本、节点、依赖、输入输出契约、计划 Agent、验收条件和变更原因。规划版本不可覆盖。

#### 2. 实际执行 DAG (E)：实际上发生了什么

根据真实事件追加构建：接收、派发、拆解、选择 Agent、开始、交接、阻塞、重试、改派、输出、提交、拒绝、接受和人工干预等。

执行图不是“正确答案图”，而是事实记录。它可能包含失败、绕路、临时补救和偶然成功。

#### 3. 任务谱系证据图 (L)：信息和结果如何流转

```text
需求版本 → 规划版本 → 派发契约 → 节点输入
        → Agent 执行 → 节点输出 → Work Memory
        → 下游实际消费 → 最终提交 → 验收结论
```

谱系记录消息、文件、Memory、结果版本的 ID 和哈希，因而可以验证下游究竟消费了哪个版本，而不是只根据日志猜测。

### 3.2 双树对照：只发现偏差，不直接认定责任

系统比较 (P) 和 (E)，识别：

- 结构差异：缺少节点、计划外节点、依赖方向改变、串并行变化；
- 语义差异：目标、约束、输出格式或验收标准丢失；
- 分配差异：计划 Agent 与实际 Agent 不同；
- 输入输出差异：文件、Memory、版本或哈希不一致；
- 时间状态差异：超时、乱序、重复执行或旧结果复用。

差异本身不是根因。例如执行图比规划图多一个“数据验证”节点，可能是合理补救，也可能是组织规划漏项。系统必须结合验收结果和谱系继续分析。

### 3.3 逆向谱系回溯与因果干预

从失败的验收条件开始向上回溯：

```text
验收失败
  ← 哪项条件失败
  ← 哪个节点负责
  ← 该节点实际消费了什么
  ← 输入来自哪个结果版本
  ← 上游输出是否满足当时契约
  ← 偏差何时出现、是否传播、是否被修复
```

系统先生成根因候选，而不把候选当作最终结论。候选例如：

- 交接时丢失时间范围约束；
- 下游消费了旧结果版本；
- 数据收集 Agent 来源验证能力不足；
- 任务拆解漏掉了验证节点；
- 外部工具在关键阶段失败。

对于每个候选执行局部反事实干预或重放：

```text
干预 A：恢复丢失的时间范围约束
干预 B：改用 result_v2
干预 C：替换数据 Agent
干预 D：删除错误依赖边
干预 E：模拟工具正常返回
```

比较“只改变这一项、其他条件尽量保持不变”时最终结果是否改变：

- 恢复后成功率显著提高：更可能是主要原因；
- 只改善中间质量但最终仍失败：更可能是促成因素；
- 干预后没有影响：不应把它路由为主要进化对象；
- 多个干预都必要：记录为组合原因，而不是强行选一个责任人。

因此，“首次有效偏差”不是简单的“第一个异常节点”，而是满足以下条件的候选：出现较早、证据充分、能沿谱系解释影响，并且反事实干预能够改变结果或显著改善关键验收指标。

### 3.4 双树差异的最小修复搜索

执行图不能直接复制为下一次规划，因为执行过程中可能出现临时重试、偶然绕路和人工补救。系统要寻找的是**可复用的最小修改集合**。

定义候选修改集合：

```text
Δ = {新增/删除/替换节点，修改依赖边，补充契约字段，
     更换 Agent，增加输入检查，增加版本校验，调整披露策略}
```

每个候选修改都有代价：

- 结构修改成本；
- 额外延迟和计算成本；
- 新增通信和隐私成本；
- Agent 更换成本；
- 对其他任务的潜在负面影响。

系统采用逐步的最小差异修复搜索，而不是一次性追求“执行图越像规划图越好”。成功执行图只提供候选修改来源，失败执行图、局部正确节点、补救路径和反事实干预结果也都可以生成候选：

1. 从原规划 (P) 出发；
2. 生成一个或多个最小修改；
3. 在历史任务上回放，或在模拟环境中局部重放；
4. 保留能改善验收结果且代价较低的候选；
5. 继续扩展下一层修改；
6. 当收益不再增加或达到预算时停止；
7. 从非支配候选中选择相对最优方案。

可以使用 best-first search、beam search 或基于代价的 A* 变体。目标不是找到理论上唯一的最优路径，而是在给定任务分布、隐私约束和资源预算下，找到稳定、低成本、可回滚的相对优解。

候选方案可以按照以下目标排序：

\[
Score(\Delta)=Benefit(\Delta)-\alpha\,EditCost(\Delta)
-\beta\,RuntimeCost(\Delta)-\gamma\,PrivacyRisk(\Delta)
-\eta\,NegativeTransfer(\Delta)
\]

其中 `Benefit` 表示验收质量和成功率提升，`EditCost` 表示相对原规划修改了多少节点、边、契约和 Agent，`RuntimeCost` 表示新增延迟和资源，`PrivacyRisk` 表示修改后额外的信息披露，`NegativeTransfer` 表示它对其他任务造成的性能下降。

例如：

```text
原规划：收集数据 → 写报告
成功执行：收集数据 → 验证来源 → 修正数据 → 写报告

候选修复 1：永久增加“验证来源”节点
候选修复 2：给数据 Agent 增加来源验证 Skill
候选修复 3：在交接契约中增加 source_status 字段
候选修复 4：增加版本检查，但不改变任务结构
```

系统通过多任务回放和局部干预判断哪一种修改最值得复用，而不是盲目复制整条成功执行路径。

#### 迭代搜索示例

```text
第 0 轮：原规划
  收集数据 → 写报告

第 1 轮：尝试一个最小修改
  A. 增加 source_status 契约字段
  B. 增加输入版本检查
  C. 更换数据 Agent
  D. 增加独立验证节点

第 2 轮：保留有效候选并继续组合
  A + B
  A + C
  A + D

第 3 轮：发现 A + B 已达到目标，
        继续增加 D 只提高少量质量却显著增加成本

最终：选择 A + B，
     而不是复制“验证、失败、重试、人工修正”的完整执行路径
```

搜索结果不是一条对所有任务都固定的路径，而是一组带适用条件的修复规则。

### 3.5 条件化组织策略：复杂结构必须具体情况具体分析

组织不能因为一次任务加入额外节点后成功，就永久把所有任务都变复杂。每个组织候选需要同时携带适用条件：

```json
{
  "change": "增加独立来源验证节点",
  "applicableWhen": {
    "taskType": "external_data_analysis",
    "sourceCount": { "gte": 2 },
    "sourceConfidence": { "lt": 0.8 },
    "deliveryLevel": "formal"
  },
  "expectedBenefit": 0.17,
  "expectedLatencyCost": 0.08,
  "evidenceTaskCount": 24,
  "confidence": 0.89
}
```

系统需要分别验证：

- 在条件满足时，复杂结构是否显著提高成功率或质量；
- 在条件不满足时，是否可以安全地采用更简单结构；
- Agent 能力提升后，原来的额外节点是否仍然必要；
- 新结构带来的收益是否大于延迟、成本和隐私代价。

因此，组织进化的目标不是“结构越来越复杂”，而是学习：**什么条件下需要哪种结构，以及什么时候可以把临时补丁删除。**

### 3.6 组织—个体双层优化

联合进化不是“组织候选和个体候选各自随便更新”，而是把它们定义为两个相互影响的层级。

#### 上层：组织策略

组织层决定：

- 任务如何拆分；
- 哪些依赖串行、并行或可选；
- 如何设计交接契约；
- 如何选择和分配 Agent；
- 何时需要验证、重试或重新规划；
- 共享信息的披露等级和权限边界。

#### 下层：个体 Agent 能力

个体层决定：

- Skill 和工具使用能力；
- 输入检查和版本检查习惯；
- 结果验证能力；
- Memory 和记忆摘要方式；
- 能力画像标签和能力权重；
- 对特定任务类型的置信度。

两层之间双向反馈：

```text
组织发现反复缺少来源验证能力
  → 组织生成“增加来源验证节点/契约字段”的候选
  → 个体 Agent 生成来源检查 Skill 候选

个体 Agent 在多个任务中稳定形成新能力
  → 组织更新任务拆分和能力匹配
  → 后续任务减少重复验证或把该 Agent 分配到更合适的节点
```

执行图是证据轨迹，进化候选是从证据中提取的最小可复用修改；规划图向执行图靠近只是候选生成的一个来源，不是优化目标本身。

双层优化可以交替进行：

```text
固定当前 Agent 能力：
  搜索更合适的任务结构、依赖、契约和分配方式

固定当前组织策略：
  判断哪些失败仍然来自个体 Skill、Memory、工具或检查能力

Agent 能力发生变化后：
  重新评估组织中的验证节点、冗余节点和候选排序

组织任务分布发生变化后：
  重新决定 Agent 应优先学习和保留哪些能力
```

正式选择时至少比较四种方案：不更新、只更新组织、只更新 Agent、组织与 Agent 联合更新。联合方案只有在多任务收益高于单层方案时，才能被称为“联合进化有效”。

### 3.7 防止“成功一次就学错”的机制

“某次执行成功”只能说明这一次路径成功，不能直接证明组织结构或 Agent 修改普遍有效。原因可能是人工临时补救、随机重试、评测器误判、调用了更强但更贵的模型，或该路径只适合当前任务。

因此采用以下门控：

1. **单次任务**：只记录诊断和候选，不改变长期策略；
2. **同类任务重复出现**：候选进入历史回放；
3. **离线回放有效**：进入小流量或 canary 验证；
4. **多任务稳定收益**：才正式写入组织策略或 Agent 能力；
5. **出现负迁移**：自动降低权重或回滚。

具体情况还要具体分析：若增加复杂组织结构只是在弱 Agent 上提供了额外保护，而没有提升 Agent 本身能力，系统应优先判断是短期组织补丁还是长期个体学习；若交接协议缺字段，则不能只给下游 Agent 增加“猜测缺失信息”的 Skill。

### 3.8 归因和进化对象路由

| 观察到的原因 | 优先修改对象 |
|---|---|
| 需求歧义导致规划方向错误 | 需求澄清和意图识别策略 |
| 任务拆解漏掉必要工作 | 组织级任务模板和规划器 |
| 依赖顺序或方向错误 | 组织 DAG 和调度策略 |
| 协作者选择不匹配 | 能力画像、候选排序和负载策略 |
| 交接时丢失约束 | 结构化任务契约和上下文投影 |
| 下游消费旧结果 | 版本协议、消费确认和输入检查 |
| 个体反复不能完成同类操作 | 对应 Agent 的 Skill、Memory 或工具策略 |
| 验收器错误或标准不完整 | 验收器和质量门控 |
| 网络、工具、存储或模型故障 | 基础设施、重试和恢复机制 |

一个任务可以同时产生多个不同层级的候选，但只有证据支持的候选才能进入自动更新。

## 四、完整算法流程

```text
1. 创建需求版本和隐私策略
2. 发起方生成跨 uBuddy 的初始规划 P0
3. 各接收方逐步补全内部规划 P1...Pk
4. 根据当前决策启动 CAD 最小充分披露
5. 记录实际事件，构建执行 DAG E
6. 记录输入、输出、Memory 和结果版本谱系 L
7. 对照 P 与 E，生成结构/语义/分配/版本差异
8. 从验收失败点沿 L 逆向回溯
9. 生成多个根因候选
10. 对候选执行局部反事实干预或重放
11. 生成组织修改、个体修改和信息披露修改候选
12. 搜索代价最小且收益稳定的差异修复集合
13. 在 benchmark 的多任务、多轮次上验证
14. 通过证据门控后进行 canary 发布
15. 监测收益、成本、隐私风险和负迁移，必要时回滚
```

## 五、Benchmark 验证方案

### 5.1 为什么需要多任务 Benchmark

单个案例中“原规划无法继续、执行图后来成功”只能说明该案例存在有效补救，不能证明修改在未来任务中普遍有效。要验证联合进化，需要让系统在一批同类但不完全相同的任务上经历多轮：

```text
第 1 轮：暴露问题并记录证据
第 2 轮：使用候选组织/个体修改
第 3 轮及以后：检测收益是否稳定、是否出现负迁移
```

Benchmark 必须将“生成候选”和“证明候选有效”分开：

```text
训练任务：发现失败模式、学习披露先验、生成修复候选
验证任务：选择阈值、搜索预算和候选组合
隐藏测试任务：评价未见任务上的成功率、隐私风险和迁移效果
长期任务流：评价连续更新后是否漂移、退化或不断增加复杂度
```

不能在同一批任务上根据成功执行图生成修改，再用这些任务证明修改有效，否则只能证明系统记住了历史路径。

### 5.2 任务构造

Benchmark 应覆盖：

- 多个用户和组织；
- 不同隐私等级；
- 结果版本更新和过期；
- 约束在交接中容易丢失的任务；
- 需要多个下游消费者的 DAG；
- 工具失败、网络延迟和 Agent 能力不匹配；
- 可明确验收的最终交付物。

每个任务保留隐藏的“真实故障注入标签”，例如：约束丢失、旧版本消费、错误分配或工具故障，用于评价归因准确率，而不直接暴露给系统。

除了人工构造故障，还应保留一部分自然失败任务，并由多名标注者根据完整日志给出主要原因、促成因素和传播路径。这样可以同时测试方法在可控故障和真实复杂故障上的表现。

### 5.3 对比方法

- 完全不共享跨主体状态；
- 完全共享所有上下文；
- 固定字段共享；
- 普通共享 Memory/blackboard；
- 只做规划—执行差异检测；
- 只做最后责任节点归因；
- 只做组织更新；
- 只做 Agent 更新；
- **本文方法：CAD + 双树谱系因果干预 + 最小差异修复 + 双层联合优化**。

### 5.4 主要指标

任务侧：成功率、质量、延迟、成本、重试次数、人工介入次数。

隐私侧：敏感字段暴露率、隐私攻击成功率、披露 token/字节数、受控查询次数。

协作侧：版本错配率、约束保留率、重复劳动率、不必要等待时间、依赖阻塞识别准确率。

归因侧：根因定位准确率、主要/促成因素区分准确率、传播路径 F1、误惩罚率、证据覆盖率。

进化侧：后续同类任务收益、跨任务迁移、负迁移率、更新成本、回滚次数。

### 5.5 必要消融

至少需要分别去掉：

- 反事实披露；
- 谱系信息；
- 反事实因果干预；
- 最小差异修复搜索；
- 组织层更新；
- 个体层更新。

这样才能回答：性能提升究竟来自更多日志、更多共享信息，还是来自本文提出的自适应披露、因果干预和双层优化机制。

## 六、论文中应明确的贡献表述

建议不要把贡献写成“我们实现了一个包含很多模块的协作平台”，而写成以下三个可验证命题：

1. **最小充分披露命题**：在跨用户信任边界下，CAD 能针对不同任务动态选择协作信息，在保持任务效用的同时降低披露量和隐私风险。
2. **因果归因命题**：渐进式规划 DAG、实际执行 DAG 和谱系证据结合局部反事实干预后，比末端归责或首次异常规则更准确地识别真正影响结果的原因。
3. **联合进化命题**：从成功补救和失败传播中搜索最小差异修复，并同时更新组织策略与个体 Agent 能力，比静态策略、只改组织或只改 Agent 在多轮 benchmark 上取得更稳定的收益。

## 七、方法边界与诚实表述

本文不声称：

- 一次成功执行就证明了某个修改普遍正确；
- 执行图一定比规划图更优；
- 任何最早异常都是根因；
- 所有问题都应该归因到 Agent 能力；
- 共享的信息越多，协作就一定越好。

本文真正主张的是：

> 在跨用户、多组织 Agent 协作中，用面向决策的最小充分披露减少不必要的信息暴露，用双树和谱系记录事实，用反事实干预检验原因，再用最小差异修复和组织—个体双层优化寻找能够跨任务复用的改进。
