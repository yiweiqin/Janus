# uBuddy 跨人 Agent 协作全链路（简单说明版）

## 1. 一句话说明

用户提出一个复杂任务后，发起方 uBuddy 先把任务交给合适的其他用户 uBuddy；每个接收方 uBuddy 再根据自己的 Agent 能力拆分子任务。所有参与者通过同一份公开协作状态了解任务进展、依赖和结果版本，Agent 自己决定下一步怎么做，系统负责把信息完整、及时、可追溯地传递给相关参与者。

这里的“图”不是图片，而是机器内部保存的结构化协作状态。人类在前端看到的是“组织协作看板”，Agent 看到的是经过权限过滤的文本/JSON 状态。

## 2. 示例任务

Alice 想完成一份市场分析报告，需要：

- 收集行业数据；
- 验证数据来源；
- 制作图表；
- 整理最终报告。

参与者可能是：

```text
Alice uBuddy
├── Bob uBuddy：负责数据分析
└── Carol uBuddy：负责图表和报告整理
```

Bob 和 Carol 不需要把自己的私有会话、私人 Memory 或本地文件暴露给 Alice。系统只同步本任务允许公开的目标、状态、摘要、结果版本和依赖信息。

## 3. 全链路总览

```text
用户提出任务
  ↓
发起方 uBuddy 理解任务
  ↓
必要时向用户请求澄清
  ↓
查询参与者能力并发起委托
  ↓
建立组织协作看板和共享 Work Memory
  ↓
接收方 uBuddy 接收公开任务要求
  ↓
接收方 uBuddy 拆分自己的 Agent 子任务
  ↓
协作规划逐步补全并保存多个版本
  ↓
Agent 开始执行并持续发布公开状态
  ↓
系统更新节点、交互、结果版本和依赖集束
  ↓
相关 Agent 读取最新状态并自主决定下一步
  ↓
任务结果交接、修订、提交和验收
  ↓
系统保留全过程证据
  ↓
根据规划与执行的差异分析组织和个体如何改进
```

## 4. 第一步：用户提出任务

用户先告诉自己的 uBuddy：

```text
请完成一份市场分析报告，需要数据、竞争分析、图表和最终汇报材料。
```

发起方 uBuddy 负责整理：

- 任务目标；
- 交付物；
- 验收标准；
- 时间要求；
- 执行约束；
- 哪些信息可以公开；
- 哪些内容必须保持私有。

如果缺少会影响任务方向的重要信息，uBuddy 会提出结构化澄清问题，例如：

```text
最终交付物是：
1. 只要一份 PPT；
2. 一份分析报告加一份 PPT？
```

澄清不是系统随意打断任务，而是 uBuddy 判断当前信息不足后提出的问题。问题、选项、用户回答都会被保存，回答后形成新的需求版本。

## 5. 第二步：选择协作者

发起方 uBuddy 查看授权范围内的能力画像：

```text
Bob：行业研究、数据分析、数据清洗
Carol：PPT 制作、图表设计、汇报材料
```

然后建立外部委托或任务群：

```text
Alice uBuddy
├── Bob uBuddy：完成数据分析
└── Carol uBuddy：完成图表和汇报材料
```

此时发起方只需要规划跨用户的工作范围，不需要提前知道 Bob 和 Carol 内部的全部 Agent。

## 6. 第三步：建立协作状态和共享 Work Memory

系统建立“组织协作看板”的机器数据，包括：

- 根任务节点；
- Bob、Carol 的 uBuddy 节点；
- 委托关系；
- 父子关系；
- 初始依赖关系；
- 参与者权限；
- 当前图版本号。

同时创建当前任务的共享 Work Memory。它只保存允许公开的工作信息，例如：

```text
数据收集已经完成；当前有三个公开数据源；来源验证尚未完成；结果版本为 market_data_v1。
```

不会公开：

- 私人聊天内容；
- 完整 Prompt；
- 私有 Memory；
- 本地真实路径；
- 凭据和密钥；
- 尚未授权的原始附件。

## 7. 第四步：接收方 uBuddy 拆分内部任务

Bob 的 uBuddy 收到公开任务后，自己规划内部 Agent：

```text
Bob uBuddy
├── Bob Agent 1：收集行业数据
└── Bob Agent 2：验证数据来源
```

Carol 的 uBuddy 规划：

```text
Carol uBuddy
├── Carol Agent 1：制作图表
└── Carol Agent 2：整理汇报材料
```

系统把各方公开子图合并到同一张协作图中，形成：

```text
根任务
├── Bob uBuddy
│   ├── Bob Agent 1：收集行业数据
│   └── Bob Agent 2：验证数据来源
└── Carol uBuddy
    ├── Carol Agent 1：制作图表
    └── Carol Agent 2：整理汇报材料
```

接收方 uBuddy 不能再向第三层外部 uBuddy 委托。若尝试继续向外委托，系统只做深度和循环校验，并返回“已达到首版协作深度限制”；不替它重新设计任务。

## 8. 第五步：逐步保存规划版本

规划不是一次性完成的，而是随着不同 uBuddy 掌握更多信息逐步展开：

```text
P0：只有总目标
P1：加入 Bob 和 Carol 两个 uBuddy
P2：Bob 补充两个内部 Agent
P3：Carol 补充两个内部 Agent
```

每次规划变化都保存新版本，旧版本不覆盖。系统记录：

- 变化前的版本；
- 变化后的版本；
- 哪个 uBuddy 或 Agent 提出变化；
- 增加、删除或修改了什么；
- 为什么变化；
- 变化时使用了哪些公开证据。

执行中的普通进度变化不产生新规划版本。例如 `running → completed` 只是执行状态更新。只有任务结构、依赖、负责人、输入输出要求或需求发生变化时，才需要新规划版本。

## 9. 第六步：Agent 执行并形成执行过程

执行层不是只保存最终状态，而是追加保存每一个重要事件：

```text
E0：节点创建
E1：Bob Agent 1 接受任务
E2：Bob Agent 1 开始执行
E3：Bob Agent 1 发布数据 v1
E4：Bob Agent 2 接收数据 v1
E5：Bob Agent 2 发现来源不完整
E6：Bob Agent 2 发布审核意见
E7：Bob Agent 1 发布数据 v2
E8：Carol Agent 1 读取 v2
E9：Carol Agent 1 开始制作图表
```

节点当前显示的状态只是事件历史的最新投影。例如一个节点现在是 `completed`，它以前经历过的 `blocked`、`retry_wait`、旧结果和修订记录仍然保留。

系统中可以同时存在：

- 当前节点状态；
- 完整任务事件；
- 多个结果版本；
- 每个结果的采用、淘汰或拒绝状态。

因此前面的过程不会被覆盖。

## 10. 第七步：记录依赖集束

依赖边是结构化数据，不是简单的文字箭头。例如：

```text
Bob Agent 2 → Carol Agent 1
```

机器中表示为：

```json
{
  "kind": "dependency_of",
  "fromNodeId": "bob_verify",
  "toNodeId": "carol_chart",
  "dependencyBundle": {
    "data": { "status": "available", "version": "market_data_v2" },
    "logic": { "status": "partially_satisfied" },
    "quality": { "score": 0.85, "status": "pending_review" },
    "freshness": { "score": 0.92, "expired": false },
    "review": { "status": "pending" },
    "capability": { "matchScore": 0.78 },
    "resource": { "queueDepth": 2 },
    "risk": { "score": 0.25 },
    "downstreamImpact": { "score": 0.90 }
  }
}
```

依赖集束只负责描述这两个 Agent 之间的协作关系当前是什么状态。它不作为中央控制器的硬性执行条件。

## 11. 第八步：Agent 读取状态并自主协作

每个 Agent 会看到自己有权限访问的完整公共协作图，包括：

- 所有授权节点；
- 所有授权依赖边；
- 每条边的完整依赖集束；
- 结果版本；
- Work Memory 摘要；
- 阻塞、重试和修订事件；
- 下游影响和风险信息。

Agent 看到的是结构化 JSON 或文本，不是图片。例如 Carol Agent 可能看到：

```json
{
  "from": "bob_verify",
  "to": "carol_chart",
  "dataVersion": "market_data_v2",
  "qualityScore": 0.85,
  "reviewStatus": "pending",
  "freshnessScore": 0.92,
  "riskScore": 0.25,
  "downstreamImpact": 0.90
}
```

然后由 Carol Agent 自己决定：

- 直接使用结果；
- 先制作草稿；
- 等待审核；
- 请求 Bob 补充信息；
- 使用新版本；
- 重试自己的工作；
- 提出改派或重新规划。

系统只保证最新信息能够传到它那里，不代替它做这些判断。

## 12. 第九步：执行中发生计划变化

如果 Agent 发现原计划不适用，它可以自主提出重新规划：

```text
Bob Agent 2：原数据源失效，建议增加备用数据收集节点。
```

系统保存：

```text
P4：在 P3 基础上增加备用数据节点
```

同时继续保存执行事件：

```text
E10：发现数据源失效
E11：发布重新规划请求
E12：新增备用数据节点
E13：备用节点开始执行
```

系统不判断 Agent 的方案一定正确，只负责保存、校验格式、广播变化，并让其他 Agent 看见新旧版本和变化原因。

## 13. 第十步：结果交接、修订和验收

Agent 产生结果后：

```text
Agent 发布结果版本
  ↓
系统写入公开 Work Memory
  ↓
系统记录输入输出谱系
  ↓
系统更新依赖集束
  ↓
下游 Agent 读取最新状态
  ↓
相关 uBuddy 或用户自主判断是否接受
```

提交、拒绝、修改、重新提交和验收都作为独立事件保存。系统可以做权限和格式校验，但不替 Agent 或用户做最终质量判断。

## 14. 第十一步：任务结束后的原因分析

如果最终结果失败，系统不直接把责任归给最后一个 Agent，而是综合：

- 规划版本之间的差异；
- 每个 Agent 的执行事件；
- 节点输入和输出；
- Work Memory 版本；
- 依赖集束分数变化；
- 结果被谁消费、消费了哪个版本。

例如：

```text
主要原因：交接时没有传递“必须使用最新审核版本”的信息
促成因素：Bob 的数据质量较低
局部正确行为：Bob Agent 2 发现了质量问题
补救行为：Bob Agent 1 发布了 v2
末端影响：Carol Agent 1 仍然使用了旧版本 v1
```

这不是一次简单的“失败 Agent 评比”，而是对整条协作链路的分析。

## 15. 第十二步：组织和个体共同改进

原因分析结果分别进入两个方向：

组织层可能改进：

- 任务拆分方式；
- 依赖安排；
- 委托规则；
- 交接格式；
- 结果版本协议；
- 协作提示模板。

个体层可能改进：

- Agent Skill；
- Agent Memory；
- 能力画像；
- 能力权重；
- 输入检查和结果检查习惯。

例如：

```text
组织层：所有数据结果都要携带版本和审核状态。
个体层：Carol Agent 增加检查输入版本的能力。
```

候选改进需要经过后续任务验证，不能因为一次失败就立即覆盖现有策略。

## 16. 系统和 Agent 的职责边界

### 系统负责

- 保存规划版本；
- 保存执行事件；
- 保存结果和输入输出谱系；
- 更新依赖集束；
- 过滤私有信息；
- 传递公共状态和消息；
- 处理版本、权限、循环和幂等；
- 支持断线重放；
- 将图渲染成看板。

### Agent/uBuddy 负责

- 理解任务；
- 请求澄清；
- 拆分任务；
- 选择内部 Agent；
- 判断是否等待、重试或改派；
- 判断是否使用某个结果版本；
- 提出重新规划；
- 提交、修改和验收结果。

## 17. 最终概括

```text
渐进式规划树：记录原本准备怎样做
执行事件树：记录实际上发生了什么
任务谱系证据图：记录输入、输出和结果如何流转
依赖集束：描述 Agent 之间关系的实时状态
共享 Work Memory：传递允许公开的协作证据
Agent 自主决策：决定下一步协作行为
联合进化：根据完整证据同时改进组织和个体
```

核心不是“把任务画成图”，而是让所有授权 Agent 基于同一份、持续更新且不会丢失历史的协作状态自主协作，并在任务结束后能够解释问题来自哪里、应该改进什么。
