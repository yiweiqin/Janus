# uBuddy 完整技术路径讲稿（面向非本方向研究员）

## 开场：我们到底要解决什么问题

大家可以先把 uBuddy 想成一个“多人、多个人工智能助手共同完成复杂任务”的协作系统。比如，一个人负责需求分析，另一个人的助手负责数据处理，第三个人的助手负责写代码或制作报告。

传统系统通常只共享消息、任务列表和最后结果。但跨组织协作有一个现实限制：我们不能看到别人的完整提示词、记忆、文件、凭据和工具内部状态。于是系统面临三个问题：共享太多会泄露隐私，共享太少又无法决策；即使共享了状态，也可能不知道某个结果是否真的适用；任务失败后，还无法判断究竟是 Agent（人工智能代理）、关系边、版本、资源还是组织分工出了问题。

我们的完整技术路径就是：

> 先建立部分可观测的协作世界，再用任务级依赖集束表示关系状态，接着根据具体决策生成最小充分的公共语义，最后利用带证据的关系级归因推动组织和 Agent 的联合更新。

## 第一部分：部分可观测协作世界

### 1. 为什么需要“世界模型”

我们不把所有信息简单放进一张全局图，而是分成两部分：

- 公共空间：任务目标、节点、公开状态、进度、结果摘要和版本。
- 私人空间：完整 Prompt（提示词）、Memory（记忆）、文件、凭据和内部工具状态。

系统还同时保存规划图和执行图。规划图记录“原本打算怎么做”，执行图记录“实际上发生了什么”。两者不能互相覆盖，因为后面需要比较计划和真实执行之间的差异。

### 2. 算法：建立协作世界状态

第一步是读取当前任务、参与者、权限和历史先验。第二步为每个节点和关系登记 Owner（责任方）、交付义务、允许披露范围和公共契约。第三步生成当前一致状态，也就是所有已知公共事件都能解释、且不违反权限和版本约束的状态集合。

可以把它理解成：系统不声称知道唯一真实世界，而是维护一组“目前仍可能的世界”。这组世界是后续判断能否做出稳定决策的基础。

## 第二部分：任务级依赖集束 TDB

### 1. TDB 是什么

TDB（Task-scoped Dependency Bundle，任务级依赖集束）不是一个简单的依赖分数，也不是静态的 Agent 能力标签。它绑定四类信息：

1. 哪个任务；
2. 哪条关系边；
3. 哪个时间点；
4. 哪个接收者正在询问什么、允许做什么动作。

因此可以写成 `TDB(任务, 关系, 时间, 查询, 动作集合, 接收者)`。

### 2. TDB 中记录什么

每条关系边都维护 data（数据依赖）、logic（逻辑依赖）、quality（质量）、freshness（新鲜度）、review（审查）、capability（能力匹配）、resource（资源）、risk（风险）、impact（影响）和 uncertainty（不确定性）。

每个维度都带有 version（版本）、evidence reference（证据引用）、confidence（置信度）、expiry（过期时间）、Owner 和 obligation status（义务状态）。

例如，结果 R1 可能“已经生成”，但它的版本过期、质量未审查，或者不满足下游当前任务的输入条件。普通的“完成”状态看不出这些差别，TDB 可以表达出来。

### 3. 算法：TDB 的事件驱动更新

系统接收 publish（发布）、consume（消费）、review（审查）、timeout（超时）、retry（重试）、handoff（交接）、version change（版本变化）和 failure（失败）等事件。

每个事件只更新受影响的关系边，而不是重写整个协作图。TDB 经历三个阶段：

```text
TDB-plan：计划中的依赖状态
→ TDB-active：执行中的动态状态
→ TDB-exec：任务结束时的最终状态
```

这三个阶段形成 TDB-Trace（依赖集束轨迹）。它保存状态如何变化，而不是只保存最后一个分数。

### 4. 为什么 TDB 是核心创新

同一个 TDB 同时回答三个问题：应该向谁披露什么信息？结果问题更可能来自哪条关系？哪些经验可以进入下一次更新？

这也是它与普通 Graph Memory（图记忆）、Trace Graph（轨迹图）和 Capability Profile（能力画像）的区别：TDB 是任务关系和当前决策绑定的状态对象。

## 第三部分：决策充分的公共语义投影

### 1. 为什么“共享状态”还不够

下游接收者通常不是想了解所有信息，而是要做一个动作，例如：消费哪个结果、是否等待、是否重试、是否改派、是否发布。

同一份公共摘要可能对应多个私有世界。在一个世界里应该消费 R1，在另一个世界里应该等待 R2。如果动作不同，就说明当前公共语义不充分。

### 2. 算法：条件化渐进披露

我们把可披露内容切成语义单元，例如状态、结果摘要、版本范围、质量证据、局部 Work Memory（工作记忆）和补充证明。

披露采用四级策略：

```text
L0：节点状态和进度
L1：结果摘要、版本和适用范围
L2：必要的工作记忆、局部证据和依赖维度
L3：受控查询、补充证明或 Probe（探测干预）
```

每次选择信息单元时，计算它对当前决策稳定性的提升与披露成本的比值。系统优先披露最可能改变决策的最小单元，而不是全量公开。

### 3. 决策充分性的判断

对当前公共历史，我们维护一致私有世界集合。若在这些世界中存在同一个授权动作，并且该动作的最坏 regret（遗憾）不超过 ε（允许误差），则生成 DSC（Decision-Sufficient Certificate，决策充分证书）。

证书至少包含：

- decision query（决策查询）；
- action set（动作集合）；
- regret bound（遗憾上界）；
- disclosure cost（披露成本）；
- evidence references（证据引用）；
- contract hash（契约哈希）；
- expiry（过期时间）；
- next action（下一步动作）。

输出有三种：

- `CERTIFIED`：当前公共语义足以支持指定动作；
- `CONFLICT`：不同一致世界支持互斥动作；
- `UNKNOWN`：证据、权限、支持或预算不足，无法安全判定。

这里的 `CERTIFIED` 不表示系统看到了真实私有状态，只表示对当前查询，决策已经足够稳定。

## 第四部分：依赖证据归因和联合进化

### 1. 为什么不能看到失败就修改 Agent

任务失败可能来自任务拆分、关系交接、旧版本、资源拥塞、信息披露不足或 Agent 能力不足。如果直接把失败写入某个 Agent 的 Skill（技能）或 Memory（记忆），就会产生错误更新和跨任务负迁移。

### 2. 两种归因证据

观察性轨迹只产生责任信念：

`b(c)=P(c | TDB-Trace)`。

它表示“现有证据更支持哪种解释”，但不是因果结论。

要得到干预支持的效果，需要执行受控 Probe，例如 replace Agent（替换 Agent）、change Edge（改变依赖边）、refresh Version（刷新版本）、add Review（增加审查）或 change Order（改变执行顺序）。比较干预前后的结果增量：

`ι(c)=E[Y | do(c=1)] − E[Y | do(c=0)]`。

只有存在权限、版本和执行支持时，才报告 `ι(c)`。

### 3. 组合关系的交互算法

有些问题单独修一条边没有效果，必须同时修两条边。对两条边 `e1` 和 `e2`，我们计算：

`I(e1,e2)=ΔY(e1,e2)−ΔY(e1)−ΔY(e2)`。

如果交互项明显不为零，就不能把单边贡献简单相加。系统会把联合修复作为一个候选集合。

### 4. 最小更新合成

候选更新可能作用于四个层次：组织结构、Agent 能力、依赖边估计和公共投影策略。系统寻找成本最低、满足安全约束并达到收益下界的更新集合。

这里要区分三种“最小”：inclusion-minimal（包含最小）、minimum-cost（成本最小）和 robust-minimal（对所有一致世界都成立的稳健最小）。论文中必须明确当前算法保证哪一种。

## 第五部分：治理式联合进化

联合进化不是自动修改所有 Agent，而是一个受治理的候选更新流程：

```text
proposal（提出候选）
→ shadow evaluation（影子评估，不影响线上）
→ cross-task calibration（跨任务校准）
→ canary（小范围灰度）
→ monitored adoption or rollback（监控采用或回滚）
```

跨任务校准会检查任务类型、关系类型、样本量、时间衰减、适用范围和置信区间。只有收益下界为正、归因排序稳定、契约未被弱化、并且存在失效触发器时，更新才会被采用。

HDBP（Historical Dependency Bundle Prior，历史依赖集束先验）只用于初始化新任务的 belief（信念）和匹配策略，不能覆盖当前实时 TDB。

## 第六部分：完整闭环总结

完整路径可以概括为：

```text
部分可观测世界建模
→ 任务级关系状态 TDB
→ 条件化最小充分披露
→ 决策充分证书
→ TDB-Trace 归因与受控 Probe
→ 最小联合更新候选
→ 跨任务校准、灰度和回滚
→ HDBP 回流下一次任务
```

我们的核心主张不是“又做了一张协作图”，也不是“让 Agent 自动进化”，而是：

> 用同一个带版本、证据和不确定性的关系级状态对象，同时约束信息披露、协作归因和长期更新。

## 结束语

如果把整个系统压缩成一句话：uBuddy 让跨组织 Agent 协作从“交换消息和最终结果”，变成“围绕任务关系维护可追溯状态，在不泄露私有信息的前提下支持稳定决策，并把经过验证的关系级经验安全地带到下一次任务中”。
