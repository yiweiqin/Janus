# 如何人工标注依赖分和相似度

不要手改 `annotation_cards.jsonl`。用本地标注页，一次看左右两个 Agent，分开打两个 5 档分数。

## 需要几个人：3 个

| 谁 | 做什么 | 量 | 大约耗时 |
|---|---|---|---|
| 甲（标注员） | test 全部盲标一遍 | 799 | 40–60 分钟 |
| 乙（标注员） | test 全部盲标一遍，看不到甲的分 | 799 | 40–60 分钟 |
| 丙（仲裁员） | 只裁甲/乙分歧；顺手复核 development + train 的预标 | 分歧约 100–250 + 7483 | 4–6 小时 |

理由：**test 是以后唯一对外报的模型准确率来源**，一个人标等于把个人偏好当真值。所以 test 必须二人独立；分歧必须有第三人裁决。protocol 里对真实标注的要求就是「至少两名独立标注者 + 第三人仲裁，报告 Cohen κ 或 Krippendorff α」。train 只是规模监督，一个人复核预标就够，不用双标。

如果只有 2 个人：甲、乙都做 test 盲标，train/development 的复核和 test 仲裁由其中一人兼任。

> 预标降低的是**每条的时间成本**，不降低 test 需要的**独立人数**。

## 启动

在 `Janus` 目录：

```bash
npm run experiment:cpdb-annotate
```

浏览器打开终端里打印的地址，默认 [http://127.0.0.1:8766/](http://127.0.0.1:8766/)。只监听本机。

如果提示端口被占用，说明已经有一个标注服务在跑。**不要把第二个一起开着**：两个进程会各写一份标签，看到的数据可能不是同一个。先关掉旧的再用。

## 盲标：test 上和别人互不可见

`test` 切分默认是**盲标**。在「我的待标」队列里，服务端会把下面这些东西全部扣掉，直到你自己打完：

- AI 预标（`prelabel_v1` 的分数和理由）
- 参考分 / teacher 分（初始 `initDependency` / `initSimilarity`）
- **另一位标注员的分**（甲打完，乙也看不到）

这不是为了防你，是因为**预标会锚定人**。如果甲、乙都看着同一份 AI 预标打分，他们会「很一致」，但那是共享锚点造成的假一致，算出来的 κ 不能当独立可靠性证据。

顶部状态会显示这条卡现在是 `预标（AI）` / `已单标` / `双人一致` / `待仲裁` / `已仲裁`。盲标时只告诉你「有 AI 预标」，不会告诉你它打了多少。

## 三个人的操作

### 甲、乙

1. 填标注人姓名或工号。
2. 角色选 **标注员**。
3. 切分选 **test（盲标）**，队列选 **我的待标**。
4. 一条一条打两个分，`Enter` 保存。打完 799 条为止，进度看右上角 `test 我已标 n/799`。

两个人各打一遍，不要互相看，也不要中途对答案。

### 丙

1. 角色选 **仲裁员**。
2. 切分 **test**，队列 **待仲裁**。这时页面会显示甲、乙两列分数和各自备注，以及参考分；看完定一个最终值保存。
3. test 清空后，切分换 **development**，队列换 **待复核预标**，按预标复核。train 同理。

仲裁只对真正的分歧生效：给一条已经「双人一致」的卡仲裁会被服务端拒绝，避免误覆盖。

## 打标尺

每条必须同时打两个分，禁止打一个总分：

| 分数 | 问什么 | 高分例子 | 低分例子 |
|---|---|---|---|
| 依赖分 D | 规划时，左方产出是否该作为右方输入？ | 信息整理 → 文案写作 | 两个演示文稿；写作 → 整理（方向反了） |
| 相似度 S | 左方做砸了，右方能不能近邻替换？ | 文案·引用绑定 与 文案·品牌语气 | 信息整理 与 文案写作 |

标尺只有 `0 / 0.25 / 0.5 / 0.75 / 1`。两个分互相独立：同职能近邻通常 S 高 D 低；上下游通常 D 高 S 低。把「我觉得他们合作会更好」写进备注，不要偷偷加到 D 或 S 上。

## 快捷键

- `A S D F G`：依赖分 0 → 1
- `Z X C V B`：相似度 0 → 1
- `Enter`：保存并下一条

## 一致性

标完一轮后：

```bash
npm run experiment:cpdb-agreement
```

或者直接看 [http://127.0.0.1:8766/api/agreement?split=test](http://127.0.0.1:8766/api/agreement?split=test)（页面上有「看一致性」按钮）。会给出：

- `kappaDependency` / `kappaSimilarity`：Cohen κ。两人完全一致为 1，随机水平约 0。
- `exactBoth` / `withinStepBoth`：两轴都完全一致 / 都差不超过一档的比例。
- `maeDependency` / `maeSimilarity`：平均绝对差。
- `statuses`：各状态条数。

κ 低于 0.6 说明标尺没对齐，先把三个人拉到一起标 20–30 条同样的卡，统一口径再继续，别硬标。

## 队列说明

| 队列 | 含义 | 谁用 |
|---|---|---|
| 我的待标 | 我还没标过的 | 甲、乙 打 test |
| 待仲裁 | 两个标注员分歧 | 丙 |
| 待复核预标 | 只有 AI 预标的 | 丙 / 单人复核 train |
| 全部待办 | 预标 + 待仲裁 | 收尾检查 |
| 我的已标 | 我标过的 | 自查 |
| 已有人标过 | 至少一个真人标过 | 抽查 |

## 保存位置

标签写在 `experiments/cpdb_org_world/data/full/human_labels.jsonl`，是**按 `(pairId, reviewerId)` 合并的行**：一个 pair 可以有多行（AI 预标一行、甲一行、乙一行、仲裁一行），后来的人不会覆盖前一个。重新生成世界不会自动带上标签；只要 pair id 没变，合并时还能对上。

标完一批后：

```bash
npm run experiment:cpdb-apply-labels
```

写出 `pairs.labeled.jsonl` 和 `label_report.json`。**只有 `已单标` / `双人一致` / `已仲裁` 三种状态会被导出成 gold**；`预标` 和 `待仲裁` 不导出——AI 预标不是人工监督，分歧没有金标值。报告里会给出各状态条数和与 teacher 的一致率。
