# uBuddy 工程化程度审查文档

> 用途：判断一个多 Agent 协作系统是否已经从“围绕科学问题的方法”膨胀为“完整产品/平台工程”。
>
> 适用场景：论文投稿前、方法冻结前、实验设计评审前、决定哪些模块进入主论文时。

---

## 1. 审查结论先行

### 1.1 核心判据

一个系统是否过于工程化，不取决于代码行数、模块数量或部署复杂度，而取决于：

> 审稿人能否清楚地知道“哪一个科学机制导致了哪一个可重复的性能变化”。

如果一个系统包含大量协议、状态、服务和治理逻辑，但无法通过少量消融实验定位收益来源，则应判定为过度工程化。

### 1.2 顶会审稿人的典型担忧

- 主要贡献不唯一，像多个系统能力的集合。
- 方法条件一次改变太多变量，无法做因果归因。
- 形式化对象很多，但没有对应的可验证学习或决策机制。
- 工程可靠性被误写成算法创新。
- 实验验证了链路能运行，却没有验证核心假设成立。
- 论文声称“因果”“进化”“联合优化”，但证据只支持规则加权或状态记录。

---

## 2. 工程化与研究性的区分

### 2.1 工程模块的特征

满足以下任意两项，通常应视为工程基础设施，而不是主方法贡献：

- 主要目标是可靠运行、权限隔离、部署或兼容性。
- 只做数据保存、同步、校验、重放、审计或展示。
- 不改变 Agent 的决策函数，只改变状态存储方式。
- 通过大量固定 schema、枚举和规则实现。
- 删除该模块后，科学假设仍然可以用简化实现测试。
- 该模块没有独立的对照组、消融实验或理论预测。

典型例子：数据库迁移、Cloud API、worker、UI、exactly-once、幂等、权限、日志、远程运行手册。

### 2.2 研究机制的特征

一个模块更可能是研究贡献，通常需要同时满足：

- 明确解决一个此前未解决的科学问题。
- 有简洁的输入、输出和决策变量。
- 能写成可检验的假设或目标函数。
- 有独立基线和一对一消融。
- 删除它会改变可观测行为，而不仅是改变存储或部署。
- 能解释为什么在某些任务上有效、在某些任务上失效。

## 3. 七维审查量表

每项按 0–3 分评分：

- 0 分：不存在或完全不清楚。
- 1 分：有描述，但无法独立验证。
- 2 分：可验证，但边界或归因仍不清楚。
- 3 分：定义清楚、可独立消融、证据充分。

总分越低，越需要削减工程链路；但“复杂度风险”分数越高越危险。

| 维度 | 审查问题 | 0–1 分的信号 | 2–3 分的信号 |
|---|---|---|---|
| 问题集中度 | 是否只有一个主科学问题？ | 一条链路包含多个独立问题 | 能用一句话定义主问题 |
| 机制必要性 | 每个核心模块是否都不可替代？ | 删除模块只损失工程能力 | 删除模块会改变研究行为 |
| 变量可归因性 | 性能提升来自哪个机制？ | 一个 M3 打包多个能力 | 每次只改变一个机制 |
| 形式化程度 | 是否存在可计算的核心对象？ | 只有丰富 schema 和术语 | 有状态、目标、约束和预测 |
| 实验对应性 | 每个主张是否有对应实验？ | 单元测试代替方法实验 | 假设—指标—实验一一对应 |
| 证据边界 | 结论是否超出当前证据？ | 用原型宣称因果/进化 | 明确区分原型、相关性和因果 |
| 论文压缩性 | 能否压缩成一张方法图？ | 需要画完整生产架构 | 4–6 个节点即可说明方法 |

### 3.1 复杂度风险评分

以下每项计 1 分，达到 5 分以上应进行工程化削减：

- 同时维护三套以上主要图或状态系统。
- 核心对象超过五类，且没有明确主对象。
- 一个方法条件同时包含版本、恢复、归因和进化。
- 论文主图包含数据库、服务、队列、UI 或部署组件。
- 评测指标超过六类，且部分指标只反映实现正确性。
- 同时接入多个 benchmark，但没有一个主任务族。
- 关键结论依赖尚未完成的真实部署或大规模实验。
- 使用“因果”“联合优化”“自进化”等强术语，但没有干预证据。

## 4. 当前 uBuddy 链路的初评

### 4.1 当前主链

```text
需求与澄清
→ 协作者发现
→ 规划树
→ 执行事件
→ 任务谱系
→ TDB 依赖集束
→ 条件化语义投影
→ Agent 决策
→ 归因
→ 反事实
→ 组织/个体进化
→ 未见任务验证
→ 回滚与先验更新
```

### 4.2 审查结果

| 维度 | 当前判断 | 主要原因 |
|---|---:|---|
| 问题集中度 | 1/3 | 同时覆盖状态建模、披露、归因和进化 |
| 机制必要性 | 1/3 | 多数模块可降为实现或扩展机制 |
| 变量可归因性 | 1/3 | M3 同时改变画像、结果、状态、恢复、归因和进化 |
| 形式化程度 | 2/3 | 有 TDB、差异、优先级和反事实定义，但实现仍以规则为主 |
| 实验对应性 | 1/3 | A/B/C/D 覆盖广，但主方法收益难以定位 |
| 证据边界 | 1/3 | 当前文档明确承认真实因果、exactly-once 和迁移收益尚未证明 |
| 论文压缩性 | 1/3 | 当前更像平台架构，而不是单一方法图 |

**初步结论：当前版本属于“研究系统原型”，对顶会方法论文而言工程化程度偏高。**

### 4.3 当前最值得保留的研究核心

建议只保留以下三个模块作为主论文方法：

```text
模块一：部分可观测协作世界建模
  → 动态任务依赖状态 TDB

模块二：决策充分的公共语义投影
  → 针对接收者和当前决策生成最小充分信息

模块三：依赖驱动的计划—执行归因
  → 用状态差异和结果谱系解释协作失败
```

“组织—Agent 联合进化”建议作为模块三的扩展实验，而不是与前三者并列的第四个主贡献。

## 5. 逐模块审查清单

### 5.1 模块一：协作世界建模

必须回答：

- TDB 是否是论文的核心状态变量？
- TDB 的维度是否有理论或任务依据？
- 每个维度是否会改变 Agent 的可观测决策？
- 是否可以用 3–4 个维度替代当前完整 schema？
- 去掉版本、审计和持久化后，机制是否仍可运行？

建议保留：

- 部分可观测任务图；
- 上下游依赖关系；
- 可用性、质量、新鲜度、不确定性等最小状态。

建议降级：

- 稳定 ID；
- 幂等键；
- 数据库映射；
- 云端同步；
- 深度限制；
- 完整权限协议。

### 5.2 模块二：公共语义投影

必须回答：

- “最小充分”中的充分，针对什么决策定义？
- 信息量、隐私暴露和决策损失如何计算？
- 投影策略是否真正改变了 Agent 行为？
- L0–L3 是否是必要的研究变量，还是工程枚举？
- `UNKNOWN` / `CONFLICT` 是否会带来可测量收益？

建议保留：

- 接收者条件化；
- 当前决策条件化；
- 最小充分信息；
- 隐私与通信成本。

建议降级：

- 复杂证书格式；
- 完整审计信息；
- 过多披露等级；
- 前端看板展示。

### 5.3 模块三：归因与进化

必须回答：

- 归因是相关性诊断还是因果识别？
- “首次有效偏差”是否比最终结果 baseline 更准确？
- 结果谱系是否能排除错误责任归因？
- 组织更新和个体更新是否必须同时存在？
- 进化收益是否在未见任务上保持？

建议保留：

- 计划—执行差异；
- 输入输出谱系；
- 多原因归因；
- 证据不足时拒绝高置信度归因。

建议延后：

- 自动 Skill/Memory 生成；
- 组织策略自动挖掘；
- 反事实搜索空间；
- 生产级 rollback；
- HDBP 跨任务先验。

## 6. 主论文、附录和删除区的划分

### 6.1 主论文必须出现

- 一个明确科学问题；
- 一个核心状态或算法对象；
- 一个简洁的方法流程；
- 三个以内的主要机制；
- 与机制一一对应的消融；
- 任务成功、协作效率、通信/隐私成本等核心指标。

### 6.2 附录或系统章节保留

- 需求版本和规划版本；
- 事件溯源与 replay；
- 权限和脱敏；
- 结果版本和 lineage 存储；
- 故障恢复；
- 数据库和 Cloud 部署；
- UI 和实验运行器。

### 6.3 暂时移出论文主线

- HDBP；
- 多层 uBuddy 深度治理；
- 八维综合评分；
- 多 benchmark 适配器；
- 组织与个体同时自动进化；
- 未被真实实验支持的因果和 exactly-once 声称。

## 7. 实验审查规则

### 7.1 每个主张必须绑定一个实验

| 主张 | 必须有的实验 |
|---|---|
| 动态依赖状态有用 | 去掉 TDB 的对照 |
| 最小公共语义有效 | local-only、静态画像、普通共享状态对照 |
| 投影减少隐私或通信成本 | 信息量、泄露量、通信量测量 |
| 计划—执行归因有效 | 最终结果归因、自然语言轨迹归因对照 |
| 归因支持进化 | Round 1→Round 2 未见任务迁移实验 |
| 证据门控有用 | gated 与 no-gate 对照 |

### 7.2 禁止用以下证据替代方法有效性

- 单元测试通过；
- schema 校验通过；
- 状态能正确保存；
- 数据库 smoke test 通过；
- UI 能显示完整图；
- 事件可以 replay；
- 远程服务成功启动；
- 单个样例的分数提升。

这些只能证明“系统可运行”，不能证明“方法有效”。

### 7.3 实验停止条件

出现以下任一情况，应先削减链路再继续扩展：

- 主实验需要解释超过四个独立机制；
- 一个条件同时打开五个以上新能力；
- 论文无法指出单一主要指标；
- 任何模块都没有独立消融；
- 结论依赖尚未完成的真实模型实验；
- 评测结果主要来自工程不变量，而不是任务收益。

## 8. 最终审查模板

在论文冻结前，作者必须用不超过一页回答：

### 8.1 一句话问题

> 在什么场景下，什么信息或什么状态缺失，导致什么协作失败？

### 8.2 一句话方法

> 我们提出什么最小机制，使哪个 Agent 在什么条件下做出更好的决策？

### 8.3 一句话证据

> 相比哪些基线，该机制在什么任务、什么指标上带来多少收益？

### 8.4 一句话边界

> 我们没有声称解决哪些系统工程或因果问题？

### 8.5 删除测试

逐项删除以下内容，并检查论文是否仍然成立：

- 数据库；
- Cloud；
- UI；
- 事件重放；
- 多层权限；
- HDBP；
- 联合进化；
- 多 benchmark；
- 复杂状态维度。

如果删除后主假设仍可验证，这些内容就不应放在主方法中。

## 9. 推荐的收敛版本

### 研究主线

```text
部分可观测协作任务
  → 动态依赖状态 TDB
  → 面向接收者和决策的最小公共语义
  → Agent 协作决策
  → 任务成功、通信和隐私成本
```

### 扩展分析

```text
计划—执行差异
  → 结果谱系回溯
  → 过程归因
```

### 暂缓闭环

```text
归因
  → 组织策略更新
  → Agent Skill/Memory 更新
  → 跨任务进化和回滚
```

这部分可以作为后续工作或补充实验，除非已经有真实、多轮、未见任务上的统计证据。

---

## 10. 审查结论

当前 uBuddy 的工程实现价值很高，但主论文需要从“完整链路”改写为“核心机制 + 可归因实验”。

最重要的削减原则是：

> 不要删除实现能力；要删除它们在论文中作为独立创新的地位。

系统可以继续保留完整的版本、权限、同步、审计和进化代码，但论文主线应只让读者看到能够被实验单独验证的最小科学对象。
