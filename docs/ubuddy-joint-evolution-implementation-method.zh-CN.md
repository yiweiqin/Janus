# uBuddy 联合进化实现方法

本文说明两个创新点在系统中如何连起来实现。规划图和执行图不是两套独立系统，而是同一张协作依赖图谱的两个阶段视图：规划阶段先确定“准备怎样做”，执行阶段再记录“实际上怎样做”。

这里所说的联合进化，不是让组织和个体分别完成各自的自进化，而是让两者相互适配：

- 组织当前缺少什么能力，就引导相关 Agent 定向补齐；
- Agent 形成的新能力，反过来改变组织的任务拆分、依赖安排和人员分配；
- 长期不被组织需要、且没有持续价值的能力，降低进化和调度优先级。

因此，规划态、执行态和谱系回溯并不是单纯为了“找到谁出错了”，而是为了回答两个更重要的问题：

1. 组织的规划、依赖和分配策略应该如何改变；
2. 哪些 Agent 应该补充、强化或降低哪些能力。

只有使用同一批协作证据同时回答这两个问题，才能形成组织与个体双向耦合的进化闭环。

## 1. 三个基本概念

### 1.1 协作依赖图谱

图谱包含两类对象：

- 节点：任务、子任务、Agent、用户、结果、Memory 或验收点；
- 边：节点之间的依赖、委派、输入输出、交接、消费和验收关系。

底层建议保存为 DAG，因为一个上游结果可能被多个下游任务使用。界面可以用树状结构展示，但数据层应保留真实的多对多关系。

### 1.2 依赖集束

依赖集束是挂在一条边上的结构化状态。例如：

```json
{
  "from": "research",
  "to": "ppt",
  "relations": {
    "data": { "status": "available", "version": "result_v2" },
    "logic": { "status": "satisfied" },
    "time": { "freshness": 0.92, "expired": false },
    "quality": { "score": 0.85, "status": "passed" },
    "review": { "status": "pending" },
    "capability": { "matchScore": 0.78 },
    "resource": { "queueDepth": 2 }
  },
  "risk": 0.25,
  "downstreamImpact": 0.9,
  "updatedAt": "...",
  "evidenceRefs": ["event_12", "memory_v4"]
}
```

它把“这两个节点相连”升级为“它们为什么相连、现在能否继续、风险有多大”。

### 1.3 共享工作 Memory

共享 Work Memory 是任务范围内、经过权限控制的协作记忆。它保存可被其他参与者使用的工作状态，而不是个人私密对话。

典型内容包括：

- 已完成的里程碑；
- 当前进度；
- 中间结果版本；
- 等待中的依赖；
- 阻塞原因；
- 质量和审核结果；
- 下一步建议。

每个 Memory 版本应记录任务范围、发布者、Agent 实例、可见性、发布时间、内容哈希和来源游标。

## 2. 规划态：执行前冻结的预测图

规划态表示“本轮任务准备怎样完成”。它由各级 uBuddy 在执行前逐层补全：

1. 发起方 A 的 uBuddy 先根据总目标，把任务委派给 B、C、D 等 uBuddy，并规划它们之间依赖集束的组合，形成跨 uBuddy 的规划图；
2. B、C、D 等 uBuddy 再在各自任务内部，把工作分配给具体 Agent，并根据本地依赖集束补全自己的子图；
3. 各级子图合并回总规划图，形成一张完整的执行前预测图；
4. 规划图在本轮执行开始前冻结，执行过程中不直接改写。

如果需求确实发生变化，系统应以新版本重新规划，而不是悄悄修改原规划图。示例：

```text
P0：完成市场分析报告

P1：报告 = 数据收集 + 竞争分析 + 图表 + 汇总

P2：数据收集 = 获取数据 + 清洗数据 + 验证来源

P3：需求变化后重新规划
```

每个规划版本至少保存：

- 需求版本和需求哈希；
- 规划版本号和父版本；
- 规划者和规划器版本；
- 节点目标；
- 依赖集束的计划值；
- 计划使用的 Agent 和 Agent 实例；
- 输入输出契约；
- 交付物和验收条件；
- 变更原因。

旧版本不能被覆盖。这样系统可以回答：“当时为什么这样拆分和分配？”

## 3. 执行态：随依赖变化更新的真实图

执行态表示“任务实际上发生了什么”。系统先复制冻结后的规划态作为执行初始态 `E0`，随后 Agent 按规划图执行。每发生一次真实事件，就更新相关节点和依赖集束，形成 `E1、E2……En`；任务结束时，`En` 就是最终执行态。

因此，规划态相对本轮执行是静态基准，执行态则是一条动态变化轨迹。中间执行版本不能只保留最后一份，否则无法判断偏差是在什么时候产生、如何向下游传播的。

典型事件包括：

- 任务进入执行和实际派发；
- 实际 Agent 接单或拒绝；
- 节点开始执行；
- 输入接收和输出产生；
- Memory 发布和结果交接；
- 阻塞、失败、重试和改派；
- 结果提交、拒绝和接受。

每个事件都应指向：

- 任务或节点 ID；
- 对应的规划版本；
- 实际 Agent 和 Agent 实例；
- 输入输出引用；
- 相关依赖边；
- 状态变化前后的版本；
- 错误码、失败阶段或重试原因；
- 事件时间和幂等键。

执行态以规划态为起点、由真实事件持续更新，是任务真正发生过的 DAG 及其状态轨迹。

## 4. 规划态和执行态如何对照

两种状态使用同一套节点和边标识：

```text
同一个协作依赖图谱
├── 规划态：执行前由各级 uBuddy 逐层补全并冻结的预测节点、依赖和分配
└── 执行态：从规划态副本 E0 开始，执行中形成 E1/E2/.../En，En 是最终真实状态
```

对照时检查：

- 是否缺少计划节点；
- 是否出现计划外节点；
- 依赖边是否增加、删除或改变方向；
- 串行关系是否变成并行，或反过来；
- 计划 Agent 和实际 Agent 是否不同；
- 计划输入和实际输入是否一致；
- 计划输出契约和实际输出是否一致；
- 结果版本是否过期或被错误复用；
- 失败、重试和改派是否有合法原因。

合理的重新规划不应被判为错误，但必须在执行前或需求变化后产生新的规划版本并记录原因；原规划版本仍需保留。

## 5. 依赖集束如何随执行更新

每当发生事件，系统更新相关边上的依赖集束。

### 5.1 上游发布结果

```text
data.status = available
data.version = result_v2
time.freshness = 1.0
quality.status = unknown
review.status = pending
```

### 5.2 下游完成消费

```text
data.consumedBy = [ppt_node]
logic.status = satisfied
downstreamImpact = 根据下游节点数量和阻塞程度重新计算
```

### 5.3 质量审核失败

```text
quality.status = failed
risk = 上升
logic.status = blocked
downstreamImpact = 上升
```

### 5.4 结果过期或需求变化

```text
time.expired = true
data.status = stale
logic.status = invalidated
下游节点 = 等待新版本或触发局部重规划
```

调度器再根据更新后的依赖集束决定继续、等待、重试、改派、重新规划或终止分支。

## 6. 共享 Work Memory 如何参与状态传播

Memory 不替代任务图，而是依赖边上的可读证据。

例如研究 Agent 发布：

```text
已完成数据收集；来源验证还未完成；当前结果为 result_v2。
```

系统据此更新“研究 → PPT”依赖集束：

```text
数据：可用
质量：待验证
审核：未通过
风险：中
```

PPT Agent 读取到的不是一段孤立消息，而是带任务范围、版本和权限的工作状态。因此它能判断：

- 哪些内容可以先用；
- 哪些内容只能作为草稿；
- 哪些内容必须等待审核；
- 哪些工作不需要重复执行。

## 7. 从最终结果向上回溯

当最终验收失败时，从失败条件开始回溯，而不是先找最后一个 Agent：

```text
验收失败
  ↓
失败的是哪项验收条件？
  ↓
哪一个执行节点负责？
  ↓
该节点消费了哪些输入？
  ↓
输入来自哪些上游节点和 Memory 版本？
  ↓
上游输出是否满足当时的规划和契约？
  ↓
相关依赖集束何时变成风险或阻塞？
  ↓
偏差是否被后续节点完全修复？
  ↓
哪个最早偏差仍然能解释最终影响？
```

目标是寻找“首次有效偏差”，而不是最早出现的任意差异。首次有效偏差必须：

- 出现得较早；
- 有足够证据；
- 没有被后续完全修复；
- 能解释下游质量下降或最终失败。

复杂任务可以同时输出主要根因、促成因素、传播路径、局部正确行为、补救行为和证据不足项。

## 8. 归因如何决定进化对象

归因结果应带有原因类型、置信度、证据和影响路径：

```json
{
  "nodeId": "handoff_2",
  "causeKind": "task_handoff_constraint_loss",
  "confidence": 0.91,
  "evidenceRefs": ["event_12", "memory_v4", "validation_4"],
  "impactPath": ["handoff_2", "analysis_4", "final"],
  "evolutionScope": "coordination_protocol"
}
```

然后按原因路由：

| 原因 | 更新对象 |
|---|---|
| 需求理解错误 | 需求澄清和意图识别 |
| 任务拆分漏项 | 组织级拆分模板和规划 Skill |
| 依赖配置错误 | DAG、并行和阻塞调度 |
| Agent 分配错误 | 能力匹配、性能和负载调度 |
| 交接丢失约束 | 结构化任务契约和上下文投影 |
| 文件、Memory 或结果版本错误 | 版本和数据传递协议 |
| 个体能力不足 | 对应 Agent 的 Skill、Memory 和能力画像 |
| 验收规则错误 | 验收器和质量门控 |
| 网络、工具或模型故障 | 基础设施和重试机制 |

基础设施故障不能被当作 Agent 能力不足；证据不足时也不能自动修改能力或策略。

## 9. 联合进化闭环

完整流程如下：

```text
创建根任务
  ↓
保存初始规划态 P0
  ↓
A 的 uBuddy 规划跨 uBuddy 依赖集束
  ↓
各 uBuddy 补全自己的 Agent 子图并合并，冻结规划态
  ↓
根据真实事件持续更新执行态和依赖集束
  ↓
更新节点、依赖集束和共享 Memory
  ↓
将规划态与执行态对照
  ↓
从验收结果沿谱系逆向回溯
  ↓
生成带证据的多重归因
  ↓
通过权限、置信度和故障排除门控
  ↓
生成组织策略候选和个人能力候选
  ↓
在后续同类任务中验证并支持回滚
```

组织层变化会影响下一次任务的拆分、依赖顺序和 Agent 分配；个体层变化会影响下一次能力匹配和执行质量。两者围绕同一批协作证据共同更新。

## 10. 建议的数据对象

### 10.1 `task_graph_plan_versions`

保存规划版本：需求哈希、规划器版本、节点、依赖集束计划值、输入输出契约、计划 Agent 和变更原因。

### 10.2 `task_graph_node_lineage`

保存规划节点与实际节点映射：实际 Agent、父节点、输入输出引用、版本哈希、状态、错误、重试、改派和下游消费者。

### 10.3 `task_graph_attribution_diagnostics`

保存归因结果：原因类型、主要或促成标记、影响路径、局部正确行为、补救行为、证据引用、置信度、阻断原因和进化建议。

## 11. 与当前代码的对应关系

当前代码已经具备：

- 协作图节点、父子关系、依赖边和增量版本；
- 任务级共享 Work Memory 和访问审计；
- 能力画像、能力选择快照和结果版本；
- 创建、执行、失败、重试、修订、提交和验收事件；
- 组织层与个人层归因信号；
- 个人进化证据路由和组织策略候选。

仍需要补齐：

- 规划版本的正式持久化；
- 依赖集束的多维分数和事件驱动更新；
- 规划节点与实际节点的完整谱系映射；
- 文件、Memory 和结果版本的哈希链；
- 首次有效偏差的自动回溯算法；
- 组织策略自动挖掘和任务拆分自动优化；
- 跨多轮任务的联合进化效果验证。
